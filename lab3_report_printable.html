Section 2: The Flow, in Your Words

Data engineering pipelines follow the lifecycle: Source → Extract → Transform → Load → Serve. Below is how our laboratory pipeline operates across each distinct stage:

  • Source: Raw compressed CSV file (yellow_tripdata_2021-01.csv.gz) hosted on GitHub release storage, containing 1,369,765 uncleaned trip records generated by NYC Yellow Cabs in January 2021.
  • Extract: The script ingest_data.py pulls data directly via HTTP streams using pandas.read_csv() in iterator chunks of 100,000 rows, avoiding large local disk writes.
  • Transform: Type coercion using explicit schema mappings (Int64 and parse_dates), temporal boundary filtering, anomaly detection, and business logic execution inside clean(df).
  • Load: Streaming chunk inserts into PostgreSQL database via SQLAlchemy engine. Chunk 1 initializes table DDL with if_exists='replace', while chunks 2 through 14 use if_exists='append'.
  • Serve: PostgreSQL exposes tabular data on port 5432 to pgAdmin (port 8085), analytics queries, and downstream visualization dashboards.
Component Roles & Technical Rationale:

1. ingest_data.py: CLI ingestion engine built with click and SQLAlchemy. Manages network extraction, iterator chunking, schema enforcement, and database transactions.

2. docker-compose.yaml: Orchestrates two container services: pgdatabase (PostgreSQL 18 with persistent volume ny_taxi_postgres_data on port 5432) and pgadmin (port 8085), creating a shared bridge network for automatic service DNS resolution.

3. Dockerfile: Builds a slim execution environment (python:3.13-slim) using Astral uv to lock exact dependencies, providing reproducible, zero-drift pipeline execution.

Why chunks? Prevents Out-Of-Memory (OOM) crashes. 100k-row chunks maintain a constant ~120 MB RAM footprint regardless of whether the file has 1.3 million rows or 100 million rows.

Why Int64? Standard NumPy int64 cannot store nulls. When missing values appear in chunks 13–14 for passenger_count and VendorID, standard Pandas forces the column to float64 (e.g. 1.0). Nullable Int64 preserves relational integer schema integrity alongside <NA>.

Why replace on the first chunk? Creates table schema DDL cleanly on the initial batch. Subsequent chunks switch to if_exists='append' so previous chunks are preserved rather than overwritten.

Section 5: How You Cleaned It (Decisions & clean(df) Execution)

We formulated rigorous data governance decisions for each anomaly and implemented the custom function clean(df). The function adheres strictly to three data engineering invariants:

1. Non-destructive: Operates on a defensive copy (df.copy()) without mutating original input.

2. Transparent Accounting: Never drops rows silently; returns (cleaned_df, dict{rule: rows_removed}).

Section 6: Answers to Technical Questions
Q1: Why does the container reach the DB as pgdatabase, not localhost?

Inside Docker, each container resides in its own isolated network namespace with its own private loopback interface (localhost / 127.0.0.1). When code runs inside the python ingestion container, localhost:5432 attempts to connect to a PostgreSQL daemon running inside the ingestion container itself, where no database exists (resulting in Connection refused). When containers are attached to a user-defined Docker bridge network (created by Docker Compose), Docker's embedded internal DNS server (running at 127.0.0.11) automatically resolves the service name pgdatabase to the internal container IP assigned to the PostgreSQL instance. Therefore, containers communicate across the bridge network using service hostnames rather than localhost.

Q2: Why chunks, and what was wrong with replace for many months?

Part A (Why Chunks): Loading massive datasets monolithically into RAM with pd.read_csv() creates severe memory spikes proportional to file size ($O(N)$). In constrained containerized environments, this triggers Out-Of-Memory (OOM) killer crashes. Chunks establish a constant streaming memory envelope ($O(K)$ where $K=100,000$), allowing files of arbitrary gigabyte sizes to be ingested safely.

Part B (What was wrong with replace for many months): df.to_sql(..., if_exists='replace') drops and recreates the target database table from scratch on each invocation. If used across multiple monthly ingestion runs (e.g. January, February, March), each new month's run will completely destroy and wipe out the data from all preceding months! At the end of the year, only the December data would remain. The correct engineering pattern is to create the schema DDL on the first batch, followed by if_exists='append' for all subsequent chunks and months.

Section 7: What Broke (Error Encountered, Root Cause & Solution)

1. Error Hit: sys:1: DtypeWarning: Columns (6) have mixed types. Specify dtype option on import or set low_memory=False followed by ValueError: Cannot convert non-finite values (NA or inf) to integer.

2. Cause: When reading in chunks, chunks 1 through 12 contain complete integer values for passenger_count and VendorID. However, chunks 13 and 14 contain 98,352 null values (NaN). Legacy NumPy int64 cannot represent nulls, forcing Pandas to either coerce integers into float64 (e.g. 1.0) or crash during downstream integer schema loading.

3. How We Fixed It: We configured an explicit schema type dictionary using Pandas Int64 nullable integer extension and string data types: {'VendorID': 'Int64', 'passenger_count': 'Int64', 'RatecodeID': 'Int64', 'store_and_fwd_flag': 'string'}. This enabled native integer parsing alongside <NA> without schema distortion or ingestion warnings.
